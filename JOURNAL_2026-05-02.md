# Track Reconstruction — Session Journal, 2026-05-02

## Goal

Convert a waist-high phone walk-through (NH1.mp4 + NH2.mp4) plus a GPS track
(autocross.gpx) into a CARLA-ingestible autocross track: `track.xodr` (OpenDRIVE)
+ `track.obj` (mesh with road/grass/cones) so drivers can practice the course
in simulation.

## What we did today

### Tried and rejected: fixing v1 segmentation in place

`track_pipeline.py` Stage 3 used YOLOP (drivable-area, BDD100K-trained) unioned
with a LAB-chroma horizon heuristic. Both failed in autocross paddocks:

- YOLOP under-segments wide flat surfaces (highway domain bias).
- The heuristic over-segments — grass leaks into the road class.
- Switched to SegFormer-B0-Cityscapes; checkpoint only ships `pytorch_model.bin`,
  which torch 2.5.1 refuses to load (CVE-2025-32434).

Concluded the segmentation-first approach was the wrong layer to fix.

### Pivot: photogrammetry-first pipeline (`pipeline_v2/`)

Replaced bespoke depth/scale/segmentation with off-the-shelf SfM:

```
video + GPX
    → extract.py    : frames + per-frame GPS (OpenSfM project layout)
    → sfm.py        : OpenSfM via Docker → camera poses + dense GPS-anchored cloud
    → semantic.py   : Mask2Former-Cityscapes per-image labels
    → cloud.py      : labeled point cloud (TODO)
    → cones.py      : YOLO-World cones, backprojected via SfM depth (TODO)
    → export.py     : track.obj (per-class submeshes) + track.xodr (TODO)
```

OpenSfM was chosen because it natively consumes a GPS prior in bundle adjustment
(via `exif_overrides.json`), so the trajectory is GPS-anchored without a
separate Procrustes step. `uv pip install opensfm` doesn't exist (not on PyPI),
so we run OpenSfM in Docker (`opensfm:ubuntu24`, ~10 min build).

### Smoke test → bug hunt → fixes

**Smoke test 1**: 96 frames @ 0.5 fps (NH1 only). SfM produced 3 disjoint
reconstructions (71 + 20 + 5 shots). Two bugs found:

1. **OpenSfM `capture_time` type bug**: we wrote ISO strings, OpenSfM expects
   Unix timestamp floats. Fixed in `extract.py`.
2. **GPS time alignment**: assumed `creation_time` was the recording start.
   For iPhone/QuickTime it's the recording **end**. Fixed: subtract video
   duration. Verified by computing intended starts (NH1 12:56:48, NH2 13:00:43)
   — both fall inside the GPX span (12:31:35 → 13:07:47), and the 43 s gap
   between NH1 end and NH2 start matches the user's "walked back a bit before
   restarting".

**Smoke test 2**: 96 frames, widened matching (`gps_neighbors=8 → 16`,
`gps_distance=50 → 100`). 2 components (91 + 5). Dense reconstruction worked —
27 MB `merged.ply` in 2 min.

### Current run

**Production smoke test**: 1230 frames @ 2 fps, NH1 + NH2, full GPS coverage.

- Extract: ~2 min (clean, all 1230 frames have GPS).
- Detect SIFT features: 7.5 min.
- Match: in progress. Container `processes: 4` was capping CPU at 400%; bumped
  to 12 — now sustaining ~900% CPU (≈9 of 12 cores).
- Match expected ~25–30 min wall time on 12 cores; reconstruct ~5 min after.

### Tooling and diagnostics added

  by `capture_time` (the first version drew shots in dict-iteration order,
