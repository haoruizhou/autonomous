# Track Reconstruction — Session Journal

Started 2026-05-02, last updated 2026-05-03.

## Goal

Convert a waist-high phone walk-through (NH1.mp4 + NH2.mp4) plus a GPS track
(autocross.gpx) into a usable autocross simulator. Original target was a
CARLA-ingestible `track.xodr` + `track.obj`; mid-session this was redirected to
a **lightweight React/WebGL simulator** that drives the measured geometry
directly. CARLA/OpenDRIVE export is deferred.

## What we did today

### Tried and rejected: fixing v1 segmentation in place

`track_pipeline.py` Stage 3 used YOLOP (drivable-area, BDD100K-trained) unioned
with a LAB-chroma horizon heuristic. Both failed in autocross paddocks:

- YOLOP under-segments wide flat surfaces (highway domain bias).
- The heuristic over-segments — grass leaks into the road class.
- Switched to SegFormer-B0-Cityscapes; checkpoint only ships `pytorch_model.bin`,
  which torch 2.5.1 refuses to load (CVE-2025-32434).

Concluded the segmentation-first approach was the wrong layer to fix.

### Pivot: photogrammetry-first pipeline (`pipeline_v2/`)

Replaced bespoke depth/scale/segmentation with off-the-shelf SfM:

```
video + GPX
    → extract.py     : frames + per-frame GPS (OpenSfM project layout)
    → sfm.py         : OpenSfM via Docker → camera poses + dense GPS-anchored cloud
    → semantic.py    : Mask2Former-Cityscapes per-image labels
    → cloud.py       : labeled point cloud (cloud.npz)
    → cones.py       : YOLO-World cones, backprojected via SfM depth
    → export.py      : track.obj + track.mtl (CARLA-ish)
    → export_json.py : track.json (browser simulator)
    → diag.py        : QA plots
```

OpenSfM was chosen because it natively consumes a GPS prior in bundle adjustment
(via `exif_overrides.json`), so the trajectory is GPS-anchored without a
separate Procrustes step. We run OpenSfM in Docker (`opensfm:ubuntu24`).

### First successful end-to-end run (`results/sfm_full/`)

1230 frames @ 2 fps, NH1 + NH2, full GPS coverage. All 7 stages produced output:

- `cloud_with_cones.npz` — 6.8M labeled points (road / grass / cone).
- `cones.json` — 4,363 valid-depth detections clustered into **310 cones**.
- `track.obj` / `track.mtl` — 213k vertices, 402k faces, groups: road / grass / cones.
- `track.json` — 78,740 road cells, 132,955 grass cells, 310 cones (+ 54 patched
  centerline holes, see below); ~3.8 MB; consumed at `/data/track.json` in the
  frontend.

This is the first run that produced a complete, simulator-ready asset
end-to-end. Tagged in this journal as **v1 of the photogrammetry pipeline**.

### Pivot mid-session: from CARLA to a React/WebGL simulator

User decided CARLA/OpenDRIVE was no longer the immediate target. New product
target: a lightweight Three.js + R3F simulator that loads `track.json` and the
photogrammetry OBJ directly. Built under `frontend/` (Vite + React + TS):

- `frontend/src/lib/coordinates.ts` — central source↔Three.js conversion.
- `frontend/src/lib/trackLoader.ts` — schema-validated JSON loader; builds road
  / grass cell sets, height maps, and a centerline-filled corridor.
- `frontend/src/lib/trackMesh.ts` — merged `BufferGeometry` for road/grass cells.
- `frontend/src/lib/vehicle.ts` — kinematic vehicle, surface lookup (road /
  grass / outside), cone hit detection.
- `frontend/src/components/PhotogrammetryMesh.tsx` — OBJ/MTL load with the
  measured photogrammetry mesh as the visual ground; OBJ cones suppressed.
- `frontend/src/components/Cones.tsx` — instanced cones at measured positions,
  scaled by observation count.
- `frontend/src/components/SimulatorCanvas.tsx`, `Hud.tsx`, `App.tsx` — scene,
  HUD, toggles, camera modes.

Current frontend behaviour: photogrammetry mesh as visual ground; the filled
centerline corridor is **driven on but only rendered as a debug overlay** when
the user toggles "Debug grid". Driving is kinematic; no physics engine.

### QA: centerline-limited road-hole patch

User observed potholes clustered around cones (cones falling to z≈0 because the
underlying road cell was empty). Implemented in
`pipeline_v2/export_json.py::_patch_centerline_road_holes`:

1. Only consider empty cells within **3 m of `centerline_hint`** (i.e. cells
   the user actually walked through).
2. Classify a cell as a road hole only if **all 8 radial directions** find road
   nearby and **none** find grass or grid edge — this rejects road ends.
3. Fill with the median z of road cells in a small window around the hole.
4. Subtract patched cells from grass.

Reported in `track.json.counts.patched_road_holes`. First run yielded 54 patched
holes.

### Diagnostics — uncovered the upstream root cause

After the road-hole patch, the user reported the car still felt like it was
floating and that the visual mesh had two disjoint arcs. Wrote
`pipeline_v2/diag.py` to render top-down classes, per-class z histograms, the
raster of cloud z, the track.json overview, and a height profile along the
walked centerline (cloud z vs grid z vs cones).

The diagnostics revealed the **real upstream problem**: OpenSfM produced two
reconstruction components (one per video) at different absolute altitudes:

- `undistorted` (NH2, 839 shots): GPS z median **122.97 m**.
- `undistorted_rec1` (NH1, 391 shots): GPS z median **118.61 m**.

That is a **~4 m vertical offset** between two reconstructions of the *same*
physical track, even though both share the same horizontal frame. The road
z-histogram is bimodal (peaks at ~115 m and ~122 m); the road-height image
shows the inner arc nested inside the outer ring at a distinctly lower
elevation.

Conclusion: the floating / vibrating ride is **not** a frontend or grid-QA
issue. It is caused by feature matching breaking at the two sharp turns,
splitting the dataset into two components that each align to GPS independently
with a vertical bias. Per-cell averaging then surfaces the bimodality as
"potholes" along the track.

### Overnight rerun

Extended `pipeline_v2/run.py` into a single `--stage all` orchestrator that
runs extract → sfm → semantic → cloud → cones → export → diag → frontend sync.
Tightened `extract.DEFAULT_OPENSFM_CONFIG` for the rerun:

- `matching_gps_distance: 60`, `matching_gps_neighbors: 24`,
  `matching_time_neighbors: 12`, `lowes_ratio: 0.85`, `matching_use_filters: yes`.
- Looser triangulation/resection: `robust_matching_threshold: 0.006`,
  `triangulation_threshold: 0.006`, `min_track_length: 2`,
  `resection_threshold: 0.008`, `resection_min_inliers: 8`.
- `align_method: auto`, `align_orientation_prior: vertical`,
  `bundle_compensate_gps_bias: yes`.
- Bumped default sampling from 2 fps → **6 fps** (≈3,690 frames vs 1,230).

Kicked off as background task `b31v7010t`, output to `results/sfm_full_v2`,
log at `logs/run_v2.log`. A 30-minute watchdog wakeup is scheduled to monitor,
diagnose failures, and resume from the failed stage autonomously.

### Riskiest remaining unknown

Whether the rec0/rec1 split survives the rerun. If it does, the most reliable
fallback is a small `cloud.py` post-step that solves a single z-bias per
component on overlapping centerline x,y and applies it to both points and
cones before saving `cloud.npz`. This is independent of OpenSfM and cheap.
